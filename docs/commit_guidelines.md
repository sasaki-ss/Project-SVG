# ■ コミット規約

本ドキュメントは、Project SVG におけるコミットメッセージの記述ルールを定義する。

---

# ■ 目的

* コミット履歴の可読性を向上させる
* 変更内容を「事実ベース」で記録する
* 検索・追跡しやすいログを構築する
* 人間およびCodexが同じ基準でコミットメッセージを判断できるようにする

---

# ■ 基本フォーマット

コミットメッセージは以下の形式とする。

```text
[type] [対象:] 内容
```

## 構成要素

| 要素 | 必須 | 説明 |
|---|---|---|
| `[type]` | 必須 | 変更種別を記述する |
| `対象:` | 条件付き | `src/` 配下のソースコード修正では原則必須 |
| `内容` | 必須 | 変更内容を事実ベースで簡潔に記述する |

## 対象の扱い

* `src/` 配下のソースコードを変更する場合は、原則として `対象:` を記述する。
* ソースコード以外の変更では、`対象:` を省略してよい。
* `src/` 配下の変更でも対象を判断できない場合は、`対象:` を省略してよい。

## 例

```text
[add] parser: XmlNodeExtractor を追加
[update] parser: 属性抽出ロジックを修正
[fix] parser: 空属性が無視される不具合を修正
[docs] ドキュメントを更新
[chore] CMake設定を更新
[test] SvgPathParserのテストケースを追加
```

---

# ■ type一覧

| type | 説明 |
|---|---|
| [add] | 新規追加（ファイル・機能） |
| [update] | 既存機能の変更（軽微な仕様変更含む） |
| [fix] | バグ修正 |
| [refactor] | リファクタリング（挙動変更なし） |
| [remove] | 削除 |
| [docs] | ドキュメントのみ |
| [test] | テスト追加・修正 |
| [chore] | ビルド・設定・雑務 |

---

# ■ 記述ルール

## 1. 基本ルール

* typeは必須
* 内容は必須
* `src/` 配下のソースコード修正では対象を必須とする
* ソースコード以外の修正では対象を省略してよい
* 1コミット1目的とする
* 日本語で記述する
* 主語を書かない（「〜した」禁止）
* 感想・推測を書かない
* 事実のみ記述する
* 抽象的な表現を避ける

---

## 2. type判断基準

typeは変更の主目的で判断する。

| type | 判断基準 |
|---|---|
| [add] | 新規ファイル、新規機能、新規クラス、新規テストファイルを追加した場合 |
| [update] | 既存機能の仕様・挙動・性能を変更した場合 |
| [fix] | 既存の不具合、期待値違い、誤動作を修正した場合 |
| [refactor] | 外部挙動を変えずに内部構造、責務分離、命名、重複を整理した場合 |
| [remove] | 不要なファイル、処理、設定、ドキュメントを削除した場合 |
| [docs] | ドキュメントのみを追加・修正した場合 |
| [test] | テストのみを追加・修正した場合 |
| [chore] | ビルド、設定、依存関係、雑務を変更した場合 |

### 判断補足

* 実装修正と対応テスト追加が同時にある場合は、主目的のtypeを使用する
* ファイル名変更・移動は [refactor] として扱う
* 依存ライブラリ更新は [chore] として扱う
* 性能改善は [update] として扱う
* ドキュメントのみの変更は [docs] とする
* テストのみの変更は [test] とする

### 例

```text
[add] parser: XmlNodeExtractor を追加
```

```text
[update] parser: 属性抽出ロジックを修正
```

```text
[fix] parser: 空属性が無視される不具合を修正
```

```text
[refactor] parser: extract処理を関数分割
```

```text
[chore] CMake設定を更新
```

---

## 3. 対象（スコープ）判断基準

対象は、ソースコード修正において変更対象の層または機能を記述する。

代表例:

* parser
* model
* render
* loader

### 判断順序

コミットメッセージの `対象` は以下の順で判断する。

1. 変更ファイルに `src/` 配下が含まれる場合、`src/` 配下を優先して対象を決める
2. `src/` 配下の変更が1つのディレクトリに限定される場合、そのディレクトリ名を対象とする
   * 例: `src/interpreter/...` のみ変更 -> `interpreter`
3. `src/` 配下で複数ディレクトリを変更した場合、変更行数（追加+削除）が最も多いディレクトリ名を対象とする
4. `src/` 直下ファイルのみを変更し、ディレクトリ名で表せない場合は `src` を対象とする
5. 対象を判断できない場合は、対象を付けず `[type] 内容` の形式としてよい
6. `src/` 配下の変更がない場合は、対象を省略してよい

### 例

```text
src/parser/SvgPathParser.cpp を変更
-> [fix] parser: 数値トークンの分割条件を修正
```

```text
docs/commit_guidelines.md を変更
-> [docs] コミット規約の判断基準を整理
```

```text
CMakeLists.txt を変更
-> [chore] CMake設定を更新
```

```text
対象を判断できないソースコード変更
-> [update] 初期化処理を整理
```

---

## 4. 内容の記述ルール

内容は、変更内容の事実を簡潔に記述する。

### 書くべき内容

* 何を追加したか
* 何を変更したか
* 何を修正したか
* 何を削除したか
* 何を整理したか

### 避ける内容

* 感想
* 推測
* 作業者の主語
* 抽象的すぎる表現
* 変更内容が分からない表現

### OK例

```text
[add] parser: XmlNodeExtractor を追加
```

```text
[fix] parser: 空属性が無視される不具合を修正
```

```text
[refactor] parser: extract処理を関数分割
```

```text
[docs] ドキュメントを更新
```

### NG例

```text
[add] XMLパーサー作ってみた
```

理由: 感想が含まれている。

```text
[fix] parser: たぶんバグ修正
```

理由: 不確定表現が含まれている。

```text
[update] parser: いい感じに修正
```

理由: 内容が不明確。

```text
[fix] parser: 修正
```

理由: 何を修正したか分からない。

---

## 5. コミット単位の判断基準

1コミットは1目的とする。

### 同一コミットに含めてよい例

* 実装修正と、それに対応するテスト追加
* 新規機能追加と、その機能に必要な最小ドキュメント修正
* ビルド設定変更と、その設定に必要な関連ファイル修正
* リファクタリングと、それに追従するテスト名・コメントの修正

### 分けるべき例

* 不具合修正と無関係なリファクタリング
* ドキュメント整理と実装修正
* 複数機能の追加
* 指摘対応と関係ない整形・削除
* ビルド設定変更と無関係な実装修正

### 判断できない場合

コミット単位を判断できない場合は、コミットせずに理由を報告する。

---

# ■ 禁止事項

* typeを省略しない
* 内容を省略しない
* `src/` 配下のソースコード修正で、対象を判断できるにもかかわらず対象を省略しない
* 英語のみで記述しない
* 主語を書かない（「〜した」禁止）
* 感想・推測を書かない
* `[fix] parser: 修正` のように内容が分からないメッセージにしない
* `[update] parser: いい感じに修正` のように抽象的な表現を使用しない
* 無関係な変更を1つのコミットに混ぜない
* 複数目的の変更を1つのコミットにまとめない
* コミット対象の判断ができない差分をコミットしない

---

# ■ 一文まとめ

コミットは「変更内容の事実を簡潔に記録するログ」とする。
